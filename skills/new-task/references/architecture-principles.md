## 1. 需求分两类

- **功能性需求**：系统要做什么。
- **非功能性需求 / 质量属性**：系统要做得多好（多快、多稳、多省、多安全）。
- 功能决定能不能用；质量属性决定该怎么搭。功能往往显性，质量属性往往隐性，必须自己问出来。

## 2. 灵魂六问（S1 拷问、S2 质量属性都要用）

1. **规模多大？** 现在多少用户 / 数据？峰值多少？
2. **读写比？** 读多写少，还是写多读少？
3. **一致性要求？** 刚写的必须立刻读到吗？能容忍短暂不一致吗？
4. **增长预期？** 一年后涨到多少？平缓还是爆发？
5. **失败的代价？** 挂了 / 数据丢了，后果多严重？
6. **有什么约束？** 团队多大？多少时间？多少预算？有无合规？

> 在新任务流程里，六问分布在 S1-2 非功能需求拷问的前三轮：第 1 轮问 1/6（规模、约束），第 2 轮问 2/3（读写比、一致性），第 3 轮问 4/5（增长、失败代价）；第 4 轮问「有哪几种搭法、各拿什么换什么」，对应 02 的候选方案与取舍。

## 3. 十条质量属性（S2-2 逐项过）

| 属性 | 一句话 |
|---|---|
| 性能 | 延迟（单次多久）+ 吞吐（单位时间多少）；看 P95/P99，不只看平均 |
| 可用性 | 几个 9；每多一个 9，成本和复杂度数量级上升 |
| 可靠性 / 持久性 | 数据会不会丢、操作会不会错 |
| 可扩展性 | 涨上来能否靠加机器从容应对 |
| 一致性 | 多处看到的数据是否一致；强一致 vs 最终一致 |
| 安全性 | 挡攻击、防越权、保护敏感数据 |
| 成本 | 建设和运营花多少钱（常被忘掉的质量） |
| 可维护性 | 好不好改、好不好懂 |
| 可观测性 | 出了问题能否快速看出哪里坏了 |
| 可演进性 | 业务变化时能否跟着长大 |

**度量要点**（06 章）：
- 延迟：平均值会骗人，看 P95 / P99 / P999；尾延迟常是体验杀手；感知延迟有时比真实延迟更重要（流式、骨架屏、乐观更新）。
- 可用性：99% ≈ 每年停 3.65 天；99.9% ≈ 8.76 小时；99.99% ≈ 52.6 分钟；99.999% ≈ 5.26 分钟。
- **说不出数字的目标都是空话**。

## 4. 常见约束

团队规模、时间、预算、合规 / 法规、已有系统、第三方依赖。
**约束不是添堵，是帮你砍选项**；摸清约束，可行方案就剩没几个。

## 5. 没有银弹，只有取舍

任何架构决策都是用 A 换 B：
- 更快 → 常牺牲成本 / 一致性；
- 强一致 → 常牺牲性能 / 可用性；
- 高可扩展 → 常牺牲简单性；
- 快速上线 → 常牺牲可维护性。

**看得到取舍 = 想清楚了；看不到取舍 = 没想清楚。**

## 6. C4 模型（S2 / S3 的分界依据）

| 层 | 画什么 | 给谁看 |
|---|---|---|
| **Context** | 整个系统一个框 + 用户 / 外部系统 | 所有人（含非技术） |
| **Container** | 可独立运行、独立部署的大块 + 通信 + 存储 | 技术团队 |
| **Component** | 某个 Container 内部的模块 + 协作 | 开发这块的人 |
| **Code** | 类 / 函数 | 基本不画，交给 IDE |

**S2 = Context + Container；S3 = Component。**

**烂图四宗罪**：① 没有边界；② 箭头没方向；③ 抽象层次混乱（最致命）；④ 框太多。
**画图三元素**：框（有职责的东西）、箭头（标方向 + 含义）、边界（部署 / 信任 / 系统）。
**五条原则**：一张图一个抽象层次；箭头标方向和含义；框数 7±2；先 Context 再下钻；为读者画图。

## 7. 八步流程（S2 的子步来源）

| 步 | 你在干什么 |
|---|---|
| ① 澄清需求与范围 | 先问问题，圈定 MVP 边界（已在 S1 完成） |
| ② 估算规模 | 信封背面算：用户量、QPS、数据量、读写比 |
| ③ 定义核心用例 / API 边界 | 对外动作清单，挑 1~2 条主航道 |
| ④ 设计数据模型 | 核心实体、关系、每类数据的存储形态 |
| ⑤ 画高层架构 | 先 Context 再 Container，先粗后细 |
| ⑥ 逐个深入关键组件 | 挑 1~2 个灵魂部件，套合适的模式 |
| ⑦ 找瓶颈，针对性扩展 | 涨 100 倍，第一个死哪？怎么破？ |
| ⑧ 回顾取舍 / 列风险 | 放弃了什么？哪里没想清楚？ |

**流程是循环**：⑦ 发现读会爆，可回 ④ 改数据模型；⑧ 发现假设站不住，可回 ① 重新确认范围。

## 8. 估算锚点（07 ②）

- 一天 ≈ 86,400 秒，估算用 **10^5 秒**。
- 1 千万日活 × 每人每天 10 次 ≈ 1,000 QPS（平均）。
- 峰值通常是平均的 **2~5 倍**，按 ~3 倍备容。
- 读写比：社交 / 内容类常读多写少，10:1 起步。
- 一条文本记录 ~ 数百字节；一张图 ~ 数百 KB ~ 几 MB。

**估算的价值不在数字精确，而在它逼你想清楚系统会被什么压垮**：读爆？写爆？存储爆？带宽爆？

## 9. 找瓶颈（07 ⑦）

- 问：用户涨 100 倍，**第一个撑不住的指标**是什么？第二个？第三个？
- 复用估算数字；按类排查：计算 / 带宽 / 存储容量 / 连接数 / 单点。
- 每个瓶颈写：**现象**（哪个指标爆）→ **破解**（缓存 / 副本 / 分片 / 异步 / CDN / 读写分离）→ **触发条件**（何时做）。
- **不是现在就建 100 倍架构**：现在不建，但知道会死在哪、留好接缝、记下触发条件。
- 反面：泛泛说"加缓存 / 上分片"；对着不疼的地方猛敲。

## 10. ADR（08 章）

**六块**：标题 / 状态 / 背景（问题、约束、力量）/ 决策 / 考虑过的其它选项 / 取舍与后果。

**什么时候写**（三条都成立才写）：
1. 难逆转；
2. 无背景会困惑；
3. 真实取舍（有真正的备选）。

**核心**：记"为什么"比记"是什么"重要一百倍；代码和图能说明系统是什么，但说明不了为什么这么选、放弃了什么。

## 11. 接缝与技术债（08 章）

- **接缝**：将来最可能被换掉的那块，用干净接口包起来，让演进从"重写"变成"替换"。
- **技术债**：有意识的权宜之计不是错；纪律是 ① 有意识地借；② 记下来（一条 ADR）；③ 安排偿还时机（触发条件）。
- **何时升级架构**：不是旧了 / 丑了 / 别人上了就升级，而是某个真正在乎的质量属性被**真实量出来的瓶颈**卡住了才升级。

## 12. `_TEMPLATE.md` 的 14 节（S2 产物自检清单）

1. 一句话定位
2. 业务本质：解决什么问题
3. 核心需求与约束（功能 / 质量属性 / 约束）
4. 架构全景图（Container 层）
5. 组件职责（做什么 + 为什么需要）
6. 关键数据流（2~3 个场景）
7. 数据模型与存储选择（每类数据 + 为什么）
8. 关键架构决策与权衡（最值钱的一节）
9. 规模化与瓶颈
10. 安全与合规要点
11. 常见误区 / 反模式
12. 演进路线（MVP → 成长期 → 成熟期）
13. 可复用要点
14. 参考原型与延伸阅读

**两条铁律**：
1. 只讲架构，不讲语言 / 框架 / 具体库（写"内存级 KV 缓存"，不写"用 Redis"）。
2. 图一律用 **ASCII**，保证任何地方都能看、永不失效。

> 新任务的 S2 不要求一次填满 14 节；按 8 个子步产出，14 节作为自检清单。
