**IRON LAW**：步骤可以被讨论、不能默默跳过 —— 任何偏离必须在当次说出来，并在计划里留痕。

## Trigger

**事件**：用户敲 `/new-task <话题>`。**不自动触发** —— 自动识别"用户在讨论新问题"会劫持普通提问，且技能描述触发不可靠。用户的"主动进入"本身就是质量来源。

## 外部依赖（调用方式与前置条件）

**调用一律走 Skill 工具、按 id 写** —— 不要试图"敲斜杠命令"（那是给用户手动触发用的形式）。

| 技能 | 模型侧 id | 模型可调 | 前置条件 | 用于 |
|---|---|---|---|---|
| Caveman | `caveman` | ✓ | 无（`stop caveman` / `normal mode` 关） | **S1 开场前** |
| Grilling | `grilling` | ✓ | 无 | S1 / S3 |
| Planning | `planning-with-files-zh` | ✓ | **cwd 下必须能建 `.planning/`**（落点 = `$PWD/.planning/<plan-id>/`） | S2 |
| Code Review | `code-review-expert` | ✓ | **必须有 git diff**（无 diff 会反过来问用户） | S5 的审查待办行 |
| Ponytail Review | `ponytail:ponytail-review`（插件；用户手动触发是 `/ponytail-review`） | ✓ | **必须有 diff**（空 diff 落到 `Lean already. Ship.`，**不报错**，所以别指望它提醒你） | S6 |

## 阶段横幅（**每一步都必须打**，2026-09-21 用户指示）

用户提的问题原话：「我不能很清楚的知道自己在哪一个阶段」。**S1 阶段还没有三件套可看**，
所以位置感只能由输出给 —— 不打横幅，用户在 S1 全程是盲的。

**模板**（三段：抬头 / 链条 / 闭合线，链条**固定 3+3 两行**，不随终端宽度变。
横线长度固定即可，**不要试图与中文抬头精确对齐** —— 中文全角宽度算不准，追求对齐只会浪费时间）：

```
── S<n> <步名>[ · <状态注>] ──────────────────
 S1 拷问 ✓ · S2 落计划 ◀ · S3 复查拷问与风险确认
 S4 检查点 · S5 实施 · S6 收尾
──────────────────────────────────────────────
```

- **`✓` = 该步**已经跑过**（**不承诺结论仍有效**）、`◀` = 当前步、无标记 = 未到**
  —— 语义按"跑过"而非"最终完成"定，是为了让「S3 打回 → 回 S2 改 → 补一次 S3」这种
  回炉场景自洽：那时 `S3 ✓`（跑过）与 `S2 ◀`（当前）**并不矛盾**，回炉原因写在抬头状态注里。
  链条只表达"现在在哪"，完整历史在三件套里
- **`<状态注>` 槽位**用于当步的即时状态：S1 写轮次（`第 2 轮（下限 2 已满）`）；
  被 S3 打回重做时写原因（`S3 翻出计划错误，回炉`）；无事则整段省略
- **打的时机**：每个步骤（S1~S6）开场一行；**S1 内部每轮再打一次**（轮次是最需要位置感的地方）；
  **S3 的两段之间再打一次**（抬头状态注写 `风险确认段` —— 从"挑计划的错"切到"逐条拍板"是两次不同的动作，
  且都要弹框，用户得知道自己在哪一段；两段共用同一行的步名，不新造词）
- **弹框 `header` 顺带带阶段**（`AskUserQuestion` 的 `header` 本来必填，填阶段几乎零成本；
  弹框是用户唯一必看的东西，横幅可能被滚动刷掉）
- **横幅走正常文字，不受 `caveman` 压缩** —— 它是导航信息不是叙述，压掉就等于没打（见反模式）
- 链条里的步名固定用本节步骤标题的名字，**不要临时换词**（换了用户认不出来）

## 步骤

> **动手前把本文件读完**（不长，一次读完）—— 末尾的「反模式」与「缺输入时的行为」两张表
> 是防错主力，只读到这里就开工会把它们漏掉。

- [ ] ⛔ **S1 拷问** —— `grilling`。**下限 2 轮**，未满不得进 S2；无上限
  - 开场 = 调 Skill `caveman` → **打 S1 横幅**（见上节）→ **直接弹第一批问题**，不寒暄、不确认流程
  - **呈现形式 = 弹框**：每轮用 `AskUserQuestion` 收答案 —— 推荐答案放**首项**并标"(推荐)"；需要背景就写进选项 `description`；**不要另铺长文**
  - `grilling` 的 `❓ Q / ➡️` 是它**内部的提问组织格式**：落到用户面前**一律转成弹框** —— 问题标题 → 弹框 `question`，`➡️` 推荐答案 → **首项并标"(推荐)"**，正文 → 选项 `description`；**不要照抄 markdown 块**（那等于用长文本 round 代替弹框，见反模式）
  - **每问末位加一条「解释这个问题与名词」**（2026-11-10 用户指示）：
    - 放**最后**，**不标"(推荐)"**，**不算作答** —— 命中后该问题仍留在 `frontier`
    - **真实答案最多 3 条**（弹框上限 4 选项 / 问）；答案超 3 条就**拆成两问**，不砍解释项
    - 命中 → 调 `answer-me-with-html` 渲染**一页**：问题与冲突点、出现的名词、每个选项选错的后果（**不写流程回顾、不复述推荐**）→ **重弹同一问**
    - **必须调 Skill `answer-me-with-html` 走完整流程**，不要绕过 Skill 直接手写 `am.mjs` 命令；按它的面板规范写 **2–4 个面板**（结论 callout + 名词 + 每个选项的后果；有分支/先后关系就加 flow），**不要写成一整段 + 一张表的薄页**（2026-11-11 用户指示）
    - 同批多问都命中 → **每个问题各出一页**（逐页连开，一页只讲一个问题）；**不合并成一页多面板**
    - **只有用户点选或明确调用 `/answer-me-with-html` 才出页**；AI **不得**自行渲染解释页（2026-11-10 用户原话："我没调用就不该触发"）
    - 渲染失败 / node 不可用 → 在对话里写短解释，**不阻塞拷问**
  - **事实自己查**（`grilling` 的要求）：frontier 里凡是能从环境查到的事实（项目结构、依赖、现有实现、文件内容），**派 sub-agent 查**，**不等它**（先把不依赖它的问题弹出去）；这类事实**不占弹框额度、不拿去问用户** —— 只有**决策**进弹框
  - **工具硬限制：一次最多 4 问 × 4 选项** → 超过 4 问就**分批弹**（每批 ≤4）；次要问题写进文本"我按 X 默认，除非你反对"，不占弹框额度
  - **第 1 轮 = 正常拷问**（问需求、按 frontier 推进）
  - **第 2 轮 = 固定挑战第 1 轮的结论**（找反例、找被忽略的选项、找过度声称）—— 不重复正常拷问，否则"下限"会退化成问废话的形式主义；若挑战翻出新决策，回到正常拷问（此后由 frontier 驱动）
  - ⛔ **下限满后，每轮末弹「续期框」**（2026-09-21 用户指示）—— 拷问要几轮由**用户**定
    - 问题就一句："这一轮拷问完了，要不要再来一轮？"
    - **推荐答案跟随 `frontier`**（沿用"首项即推荐"的弹框规则，把 AI 的判断放进 `description`）：
      frontier 空 → 首项「不用了，进计划(推荐)」；frontier 非空 → 首项「再来一轮(推荐)」并写明还剩几项未决
    - 选「再来一轮」→ 加一轮（正常拷问，frontier 驱动）→ **该轮末再弹**（故"无上限"是真的无上限）
    - 选「不用了」→ 进 S2
    - **frontier 空了也照弹** —— AI 只提供"还剩什么"作推荐，**不替用户决定"拷够了"**
  - **下限未满时，不得弹任何"推进 / 要不要继续"的框** —— 那是工作还没产出时的打扰（见反模式）
- [ ] **S2 落计划** —— `planning-with-files-zh`
  - 三件套（`task_plan.md` / `progress.md` / `findings.md`）落在**会话当前目录下的 `.planning/<plan-id>/`**（`planning-with-files-zh` 的命名计划机制），**不直接放在 cwd 根** —— 沿用它的解析规则，**不另立第二套解析**
  - `<plan-id>` = 短横线 slug（`[A-Za-z0-9._-]`），用任务名即可
  - 初始化：`mkdir -p .planning/<plan-id> && cp -n ~/.claude/skills/planning-with-files-zh/templates/{task_plan,findings,progress}.md .planning/<plan-id>/`
    —— 直接用模板铺，**不跑 `init-session.sh`**：上游那个脚本仍在 cwd 建文件、不建 `.planning/`（v3.25.2 已知不一致），`templates/` 与它的产物等价且格式合法。
    **必须带 `-n`**（不覆盖已存在文件）—— S3 打回重入 S2 时重跑这条命令，不能把已写的计划冲掉
  - 写活动指针：`sh ~/.claude/skills/planning-with-files-zh/scripts/set-active-plan.sh <plan-id>`
    —— 本环境 Bash 环境变量**不跨调用持久**，`export PLAN_ID` 不可靠，**只有 `.active_plan` 指针能跨调用生效**
  - **cwd 必须保持在会话当前目录**（resolver 与 hook 都取 `$PWD/.planning`），S1~S6 全程**不要在 Bash 里 `cd` 走**；落盘后用 `resolve-plan-dir.sh` 复核，解析到的必须就是刚建的目录
  - `task_plan.md` 必须写成 `### 阶段 N：名称` 结构，**每个阶段恰好一个** `**状态：** pending|in_progress|complete`；落盘后跑 `check-complete.sh --validate <路径>`（脚本在 planning 技能的 `scripts/` 下），不过就改到过 —— 这是 `planning-with-files-zh` 的格式硬校验，不是本流程加的规矩
  - `task_plan.md` 抬头写明**任务目录的绝对路径** —— 这是"三件套到底落在哪"的**唯一事后凭据**
    （解析按 `$PWD/.planning` 走，cwd 一漂三件套等于自废，而**从文件本身看不出来**）
  - `task_plan.md` 只写**自己的规划**（阶段 / 决策 / 风险）；**外部资料原文一律只进 `findings.md`**
    —— task_plan 被 hook 每轮注入，外部内容会被反复放大
  - 同时写入**审查待办行**（规格见下；**每个工作项一条**，不许合并）
  - 同时写入**风险与未验证项表**（规格见下；编号连续 `R1..Rn`；**不许空着** ——
    真没有就明写「本计划无未验证项与风险」）
  - 决策表编号连续；**推翻既有决策的条目必须留痕**（写明被取代的编号与理由）
  - *（有意不加确认门：`Push right` —— 三件套可撤销，问一次不如把计划做完一起问）*
- [ ] ⚠️ **S3 复查拷问与风险确认** —— 两段，**顺序固定、都不可跳**
  - **第一段：复查拷问** —— `grilling`，**固定一轮**
    - 呈现形式同 S1（**弹框** + 首项推荐 + **末位解释项**；>4 问分批；**含事实自查**）
    - 专抓：计划里的**自相矛盾 / 过度声称 / 写错的前提**（不抓"需求变了"）
    - 它抓的全是 AI 自己的错，靠自觉必然失效，故为固定步骤
    - 结论回写计划与 `findings.md`；**翻出新的未验证项 → 追加进风险表，编号续**
    - **若翻出重大计划错误 → 回 S2 改，改完补一次 S3**（不带着已知错误进 S4）
  - ⛔ **第二段：风险确认** —— 逐条拍板；**本步的第二道闸**，未过不得进 S4
    - **输入** = `task_plan.md` 的**风险与未验证项表**（规格见下）
    - **形式** = `AskUserQuestion` 弹框，**每批 ≤4 条**（同 S1 的弹框硬限制）；
      需要背景就写进选项 `description`，**不另铺长文**
    - **名词闸**（2026-11-12 用户反馈）：题干与选项里**第一次出现的非日常词**（尤其文件里的研究词，如「上游」「frontier」「镜像」）**必须就地换成日常说法或加一句括号解释**，不许裸搬 —— 这条对所有弹框都适用，不只 S3
    - **每条必须拿到一个出口**，三选（首项标"(推荐)"，AI 可推荐"接收"）：

      | 出口 | 含义 | 落痕 |
      |---|---|---|
      | **接收** | 已知风险，接受、不处理 | 该行标注「已接收」；理由写进 `findings.md` |
      | **解决** | 就地处理它 | 生成**新工作项**进 `task_plan.md`（S5 会按工作项给它配审查待办行） |
      | **重新确认** | 这条当场拍不了板 | 该条**回到 S2 改计划**（必要时在其前补一轮拷问）→ 改完**重跑本段** |

    - **每条末位再加一条「解释这条风险与名词」**（2026-11-10 用户指示）：**它不是出口** ——
      命中后调 **Skill** `answer-me-with-html`（走完整流程，同 S1 的面板规范：**2–4 个面板**，不写薄页）渲染一页（风险内容、名词、三个出口各自选错的后果）→
      **重弹该条**，直到拿到 接收 / 解决 / 重新确认 之一。加它之后每条正好 4 个选项，**出口仍是三条**
    - 同批命中**多条**风险（如 R2、R4 同批都点解释）→ **逐条各出一页**（逐页连开），**不合并成一页多面板**
    - **全部条目都拿到出口**后 S3 才算完成；**0 条也要明写到弹框/输出里**「本计划无未验证项与风险」，
      不静默过（同「没进列表 = 没被检查」）
    - 结果逐条回写 `task_plan.md` 与 `findings.md`（形如 `R3 接收`）
    - **软门禁**：靠"未打勾的行看得见 + AI 纪律"，**非技术强制**（同审查待办行）
- [ ] ⛔ **S4 Checkpoint** —— **本流程的最后一个人工点**，未获"开干"不得进 S5
  - **前置**：S3 的风险表**每条都已拿到用户给的出口**（接收 / 解决 / 重新确认）—— 没给完不进本步
  - 把计划当 **Brief** 摆给用户（产出了什么、为什么、指向产物本身），问一句"开干吗"
  - `Push right`：做最多的工作再问人，只问这一次
- [ ] ⚠️ **S5 实施**
  - **每个工作项开始前必须重读 `task_plan.md` 的对应段落**（硬纪律；正确性**不押在 hook 上**）
  - **编码纪律** —— 见下节「S5 编码纪律（karpathy-guidelines）」，**全文照做，不删减、不改写**
  - 遇到审查待办行即调 **Skill 工具 `code-review-expert`**（**要有 diff 才调得动**），**P0~P3 全部修复**，结论回写 `findings.md`（拒绝修复的条目必须写明理由）
  - `code-review-expert` 默认是 review-first，会弹「Fix all / P0-P1 only / 不改」问询 —— **用 S4 的「开干」授权覆盖它**，一律按「Fix all」全修；**S4 的 Brief 里要预先说明这一点**，否则每审一次停一次，违反「中途不再停」
  - **每条审查行都必须真调技能**，不得"沿用上一次已加载的口径"代跑 —— 它只吃 git diff，
    审查内容随 diff 变（2026-09-21 真作业里发生过这个偏离，见「审查待办行」节）
  - **最后一个工作项的审查通过后**，S5 才算完成 —— 不带着未修的 P0~P3 进 S6
  - 中途不再停
- [ ] **S6 收尾**
  - 调 **Skill 工具 `ponytail:ponytail-review`**（只吃 diff、只查过度设计）→ 按它的意见修改（只做收缩、不夹带功能变更；拒绝须写明理由）
  - **时机**：**全部工作项都完成、且最后一条审查行通过之后**才跑，全程**只此一次**。
    不要在某条审查行后顺手跑 —— 那时它审的是半成品，且与实施中的改动混在一起
    （2026-09-21 真作业里 S5 末条审查与 S6 收缩只隔 2 分钟，观感上像"一起跑的"）
  - 记账：阶段置 complete、进度回写 `progress.md`
  - 过一遍「完成判据」（见下）

> **S1 第 2 轮 与 S3 的分工**：前者挑战**未成文的结论**（需求理解本身错没错），后者挑战**成文的计划**（自相矛盾、编号冲突、过度声称 —— 只有落到纸面才看得见）。同一个透镜，两个对象，**不合并**。
>
> **S3 内部两段的分工**：**复查拷问**让 AI 挑自己的错（对象 = 计划文本，产出候选条目）；**风险确认**让**用户**给每条风险定去向（对象 = 风险清单，产出出口）。拷问出结论 ≠ 用户给出了出口 —— 顺序固定，**不合并**。

## S5 编码纪律（karpathy-guidelines）

> 来源：`karpathy-guidelines`，以下为原文全文，S5 实施期间全程遵守。
> 与 S6 的 `ponytail:ponytail-review` 不重复：这是**写的时候**的纪律，S6 是**全部做完后**再收缩一遍。

### 1. Think Before Coding

**Don't assume. Don't hide confusion. Surface tradeoffs.**

Before implementing:
- State your assumptions explicitly. If uncertain, ask.
- If multiple interpretations exist, present them - don't pick silently.
- If a simpler approach exists, say so. Push back when warranted.
- If something is unclear, stop. Name what's confusing. Ask.

### 2. Simplicity First

**Minimum code that solves the problem. Nothing speculative.**

- No features beyond what was asked.
- No abstractions for single-use code.
- No "flexibility" or "configurability" that wasn't requested.
- No error handling for impossible scenarios.
- If you write 200 lines and it could be 50, rewrite it.

Ask yourself: "Would a senior engineer say this is overcomplicated?" If yes, simplify.

### 3. Surgical Changes

**Touch only what you must. Clean up only your own mess.**

When editing existing code:
- Don't "improve" adjacent code, comments, or formatting.
- Don't refactor things that aren't broken.
- Match existing style, even if you'd do it differently.
- If you notice unrelated dead code, mention it - don't delete it.

When your changes create orphans:
- Remove imports/variables/functions that YOUR changes made unused.
- Don't remove pre-existing dead code unless asked.

The test: Every changed line should trace directly to the user's request.

### 4. Goal-Driven Execution

**Define success criteria. Loop until verified.**

Transform tasks into verifiable goals:
- "Add validation" → "Write tests for invalid inputs, then make them pass"
- "Fix the bug" → "Write a test that reproduces it, then make it pass"
- "Refactor X" → "Ensure tests pass before and after"

For multi-step tasks, state a brief plan:
```
1. [Step] → verify: [check]
2. [Step] → verify: [check]
3. [Step] → verify: [check]
```

Strong success criteria let you loop independently. Weak criteria ("make it work") require constant clarification.

## 审查待办行（S2 的产物规格）

**形态**：`- [ ] ↳ <工作项号> <工作项名> 审查：Skill(code-review-expert) → P0~P3 全修 → 结论回写 findings.md`

**它靠什么生效**：① `task_plan.md` 在 `Write|Edit|Bash|Read|Glob|Grep` 每次调用前被重新注入 AI 上下文；② 未打勾的方框用户看得见。**它不是技术强制**（本环境的 planning hook 只软提醒，`never blocks`）。

**粒度 = 工作项，不是改动性质**（2026-09-21 修正，**推翻 v1 的「分级」规则**）：

- **每个工作项配一条，不许合并、不许按性质归类**
- 反例（真发生过）：6 份产物按"都是作业骨架复制"并成 2 条审查行 → 实际只真调了
  1 次 `code-review-expert`，用户看到的是"实施过程中没按工作项审"
- **为什么按工作项而不是按性质**：用户要的是"每完成一个小阶段就审一次"（阶段 16 原话：
  "在每一个阶段后加一个 /code-review-expert 检查需求实现和代码问题，并修复 P0~P3"）。
  性质分类是 AI 的视角，工作项是**用户的视角** —— 他按工作项验收，就得按工作项审
- **`code-review-expert` 每条都必须真调**，**不得"沿用上一次已加载的口径"** ——
  它只吃 git diff，**审查内容随 diff 变**；不同工作项的 diff 不同，"口径相同"不成立
  （那次偏离的理由是"两条待办行 diff 完全重叠"，而实际两条审的是**不同的文件**）
- 工作项**照样每条都配**，包括"抓取清单""跑校验脚本"这类 —— 审查的是"**这一步做对没有**"，
  不只是"diff 好不好看"（抓取清单也会落进 `findings.md`，那就有 diff）
- 但**确无 diff 的工作项**（纯读代码理解、不改任何文件）**调不动** `code-review-expert` ——
  这时在该审查行里写明「无 diff，跳过」，**不假装审过**（与「缺输入时的行为」表同口径）

## 风险与未验证项表（S2 的产物规格）

**形态**：`task_plan.md` 里一张**编号连续**的清单 `R1..Rn`，每条三列：

| 列 | 写什么 |
|---|---|
| **内容** | 这条未验证项 / 风险是什么。**用日常语言写，不出现未定义的名词**；确需专有名词（如「上游」）就地用括号一句话解释 |
| **为什么未验证** | **先给出处**（哪个文件、哪张表 / 哪次拷问），再写根据 —— 出处往往自带解释，名词不必另设 |
| **一旦错了的代价** | 说清"赌注"，用户才拍得了板 |

**三个来源**：① S1 拷问残留的 `frontier` 未决项；② 计划正文里的假设（"假定 X"）；
③ S3 复查拷问翻出的过度声称（**追加，编号续**，不重排）。

**最少一行**：真没有就写「本计划无未验证项与风险」—— **不许空着**。空表 = 静默跳过
（同「没进列表 = 没被检查」）。

**它靠什么生效**：同审查待办行 —— ① `task_plan.md` 在 `Write|Edit|Bash|Read|Glob|Grep` 每次调用前被重新注入上下文；
② 没拿到出口的行用户看得见。**非技术强制**，本环境的 planning hook 只软提醒。

## 完成判据（S6 后自查）

- [ ] 三件套状态一致（阶段置 complete、`progress.md` 有会话条目）
- [ ] 每个审查待办行要么打勾、要么写明未执行的理由
- [ ] 风险表**每条**要么写明了出口（接收 / 解决 / 重新确认），要么写明未给出口的理由
- [ ] 未验证项如实列出（不写"已证明正确"）

> 只校验**有没有留痕**，不校验"结论是否正确" —— 后者是 S3 与 S4 人工点管的事。

## 终止

- **S1 中用户说"打住"** → 不落计划、不留产物、三件套不创建。
- **S2 之后叫停**（三件套已落盘）→ **保留、不回滚、不删**，在 `progress.md` 写明：停在哪个
  阶段、为什么停、下次从哪继续。产物按当前状态留在原地，**不假装完成**（该打勾的没打勾就
  别打勾）。
  - 这只是**记事规则**，**不是状态机** —— 恢复仍靠三件套本身（见反模式「为中断做状态机」）。

## 反模式

| 不要 | 为什么 |
|---|---|
| 替用户判断"这是小任务"从而跳链 | 判据分歧的代价大于跑一次链的成本 |
| 跳过 S3 复查拷问 | 它抓的是 AI 自己的错，靠自觉必失效 |
| 跳过 S3 的**风险确认**段（"这些风险我自己判断可以接受"） | 出口由**用户**给；AI 只负责把条目摆进弹框 |
| 用复查拷问的结论**代替**逐条风险确认 | 拷问出结论 ≠ 用户给出了每条的去向，两个出口 |
| 风险表空着不写「本计划无未验证项与风险」 | 空表 = 静默跳过，同「没进列表 = 没被检查」 |
| 用户选了**「重新确认」**却直接往下走 | 该条要回 S2 改完、重跑风险确认段才算有出口 |
| 用长文本 round 代替弹框 | 用户要的是"点选"而不是"读长文"；弹框 + caveman 模式才是他要的形态 |
| 把文件里的研究词裸搬进弹框 / 风险表（"上游""frontier""镜像"…） | 用户不共享这些词；第一次出现就得用人话解释，否则等于突然甩个陌生名词（2026-11-12 用户反馈） |
| 把 caveman 用到产物上 | 三件套 / 计划 / 记忆是持久化产物，必须正常文字（越界会让它们以后没法读） |
| 声称"产物/图已证明正确" | 只声称门禁**实际覆盖到的那一层**；过度声称比能力不足更危险 |
| 在 S1 **下限未满**时弹"要不要继续 / 进 planning" | 工作还没产出时的打扰 |
| 未点选就自动渲染解释页（"用户可能不懂这个问题"） | 用户要的是显式调用：没点选就不出页；自动出页打断拷问节奏 |
| 把「解释」项标成"(推荐)"，或拿它当作答 / 风险出口 | 它是旁路：解释完必须重弹同一条，出口仍是三条 |
| 把同批多条解释**合并成一页多面板** | 用户按问题 / 风险条目看页：一条一页，合并等于让他自己在一页里找对应关系（2026-11-11 用户指示） |
| 绕过 Skill **直接手写 `am.mjs` 命令**出解释页 | 不走 SKILL.md 的面板 / 组件流程，只能写出"一段话 + 一张表"的薄页；必须调 Skill（2026-11-11 用户指示） |
| 在 S1 下限满后**自行**判断"拷够了"直接进 S2 | 要几轮拷问由**用户**定；AI 的职责只是把 `frontier` 状态摆进推荐项 |
| 省掉阶段横幅（"这步很短 / 没什么好说的"） | 位置感断一次，用户就退回"不知道自己在哪"；横幅总共三行，省不出什么 |
| 阶段横幅里临时换步名 / 自造新词 | 用户靠步名认位置，换词等于把位置感弄丢 |
| 把多个工作项的审查**合并成一条** | 用户按工作项验收，合并等于替他决定"这几项可以一起过" |
| 用"沿用上次已加载的口径"**代替真调** `code-review-expert` | 它只吃 git diff，**不同工作项的 diff 不同**，口径代替不了审查 |
| 让 S6 的 ponytail 跟着某条审查行**顺手跑** | 那时审的是半成品；它要的是**全部完成后的最终 diff** |
| 自动触发本流程 | 会劫持普通提问 |
| 为中断做状态机 | 恢复靠三件套本身（`planning-with-files-zh` 的既有能力） |

## 术语

| 词 | 意思 |
|---|---|
| **Checkpoint** | 停下**等用户拍板**的时点。本流程有**三个**：**S1 末尾的续期框**（要不要再拷一轮）、**S3 的风险确认**（每条风险给出口）与 **S4**（开干吗）—— 都是"有产出之后"才问，故不违反 `Push right` |
| **审查待办行** | 计划里的一行待办，靠"重新注入上下文 + 未打勾可见"生效，**非技术强制** |
| **风险与未验证项表** | `task_plan.md` 里的 `R1..Rn` 清单（内容 / 为什么未验证 / 一旦错了的代价）；S3 的风险确认段逐条给它出口。**同为非技术强制** |
| **风险出口** | 用户对每条风险的三选：**接收**（接受不改）/ **解决**（就地生成工作项）/ **重新确认**（回 S2 改计划后重跑本段） |
| **解释项** | 弹框末位的「解释…与名词」：调 `answer-me-with-html` 出一页后**重弹同一条**。**不是作答、不是出口**；只有用户点选才出页 |
| **门禁（gate）** | **技术强制**：跑不过就过不去（hook / 断言）。本环境 planning hook 不拦 → **本流程没有真门禁** |
| **Push right** | 把人工确认点尽量往后推，做最多的工作再问人 |
| **Brief** | 检查点呈现给用户的东西：产出摘要 + 为什么 + 指向产物，**不是原始输出** |
| **阶段横幅** | 每步开场那三行（抬头 / 链条 / 闭合线），回答"我在哪、还剩几步"；S1 内每轮再打 |

## 边界（本流程不管什么）

- 不管**谁来实施**（默认当前 agent）
- 不管**产物格式**（那是各项目技能的事）
- 不管**排期/定时**（触发是用户事件，不是 schedule）
- 不重复 `loop-me` 的职责（`loop-me` 设计循环，本流程设计一次任务）

## 缺输入时的行为（不留悬空判断）

| 情况 | 怎么办 |
|---|---|
| 敲 `/new-task` 但没给话题 | 先问一句"要讨论什么"，**不猜** |
| S2 建不出 `.planning/`（cwd 只读 / 临时目录） | 说一句再决定落哪，**不静默回退到 cwd 根** |
| S5 没有产生代码改动（纯文档/知识任务） | S6 的 `ponytail:ponytail-review` 记"无 diff，跳过"，**不假装审过** |
| S5 的项目不是 git 仓库（没有 diff 可审） | 该工作项的审查行写「无 diff（非 git 仓库），跳过」，**不假装审过**；S6 的 ponytail 同处理 |
| S3 的风险表是空的、也没写「无未验证项与风险」 | 先补写那一行，再跑风险确认段；**不静默过** |
| S3 风险确认段里用户选「重新确认」 | 该条回 S2 改计划（必要时补一轮拷问）→ 改完**重跑本段**；不带着它进 S4 |
